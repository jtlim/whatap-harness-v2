# 아키텍처와 검증 정책

## Codex 중심 역할 분리

| 구성요소 | 책임 | 구현 위치 |
| --- | --- | --- |
| Codex | 요청 범위 결정, 원인 분석, 수정, 회귀·재검증, 보고와 PR | [Agent 작업 지침](../AGENTS.md) |
| Harness | 시나리오 등록, 증거 수집, 값과 판정 비교 | [검증 CLI](../verify.js), [시나리오](../lib/scenarios.js), [프로브](../lib/probe.js) |
| MCP | 사용자에게 보이는 데이터 처리와 포맷 검증 대상 | 빌드된 MCP의 `dist/index.js`, [stdio Client](../lib/mcp.js) |
| 독립 HTTP Client | 승인된 WhaTap HTTP API에서 참조 값을 별도로 조회 | [HTTP Client](../lib/http.js) |
| 보고서와 GitHub | 실제 근거의 재생성, 보안 범위에 따른 공개, 사용자의 최종 검토 | [보고 CLI](../review.js), [보고서 가이드](reporting.md) |

고정 Pipeline을 공식 경로로 사용하면 실행마다 같은 문제와 단계가 전제됩니다. 검수 대상에 따라 원인이 MCP, Harness, 인증, API 중 달라지므로 Codex가 증거를 보며 다음 작업을 정합니다. Harness는 그 결정과 독립적인 비교 및 기록을 수행합니다. 설계 흐름은 [README의 다이어그램](../README.md#동작-흐름)에서 볼 수 있습니다.

## 독립 검증

독립 HTTP Client는 MCP 응답을 그대로 믿거나 MCP 소스를 이용해 기준 응답을 만들지 않습니다. 읽기 전용 계정 토큰으로 프로젝트 접근을 확인하고 필요한 API를 직접 조회합니다. MCP는 stdio에서 실제 도구 요청을 처리합니다. 검증기는 시간 범위, 식별자, 수치, 누락과 중복, 표시 제한, 집계, 요약을 시나리오에 맞게 비교합니다. [비교 구현](../lib/validator.js)

| 영역 | 판정 범위 |
| --- | --- |
| 서버 | 최근 15분, CPU·메모리, 키·행 완전성, 표시 요약 |
| APM 통계 | 최근 15분 거래·예외 통계, 제한 안내, 표시 값·그룹 합계 및 별도 v2 집계 |
| 시계열 | 최근 5분 TPS·오류 건수의 5초 격자와 키·수치·완전성 |
| 잘못된 입력 | 잘못된 기간 요청을 오류로 거부하는 계약 |
| AI 답변 | 최근 1분 서버 CPU의 표본 수·평균·최대와 조회 조건 |

수치 비교는 MCP의 표시 정밀도를 반영합니다. MCP 표시 행 수가 요청 한도를 초과하거나 MCP의 필수 복합 키에 누락·중복이 있으면 FAIL입니다. 독립 HTTP의 키만 불완전하면 UNVERIFIABLE로 기록합니다. 독립 HTTP가 더 많은 원본 행을 제공할 수 있으며, 서버는 요청 한도와 제한 안내를 확인하고 독립 HTTP의 선두 행을 대조합니다. 초 단위 Period에서 호출 시각으로 밀리초 이동이 확정되면 시작 경계 행을 선두 표본에서 제외합니다. 서버와 APM의 표시 범위 검증은 대조 범위를 기록합니다. APM에 표시 제한이 있으면 안내된 행 범위에서 개별 값을 대조합니다. MXQL 비교는 검증된 Period 전체를 사용합니다. APM v2 집계는 Period 안에 완전히 포함되는 5분 버킷만 사용합니다. 집계 입력·페이지 누락이나 두 독립 API의 불일치는 검증 불가로 기록합니다.

### AI 답변의 독립 검증

서버 CPU 질문은 두 단계로 분리됩니다. Codex가 MCP에서 캡처한 선택 서버 행을 읽어 최종 JSON을 작성합니다. 답변을 제출한 후 Harness가 동일 구간을 독립 HTTP로 조회하여 격자 완전성, 요청 조건, 표본 수, 평균과 최대를 계산합니다. 기존 MCP 대조와 AI 답변 대조는 별도 판정이며, 정해진 질문의 JSON 응답을 대상으로 합니다. [실행 방법과 기준](usage.md#서버-cpu-ai-답변-검증)

### 시간 범위

- **상대시간**은 MCP 출력의 실제 `Period`를 파싱해 그 구간을 HTTP에 전달합니다. 기간 길이와 실제 호출의 시작·종료를 대조합니다. 기준 MCP의 초 단위 UTC 표시는 버린 소수초를 복원할 수 없으며, 밀리초 표시는 그대로 사용합니다. 초 단위 표시 때문에 교체된 경계 행을 확인하고 내부 행이 일치하면 전체 판정은 검증 불가입니다. 내부 값 차이나 다른 키 차이는 기존 실패 판정을 적용합니다.
- **절대시간**은 명시적으로 선택한 기능 검증에서 미리 고정한 종료점에 대해 원본과 후보의 시작·종료점을 같게 지정합니다. 출력 기간과 요청 기간도 대조합니다.
- 서로 다른 상대 실행은 각각의 HTTP 참조와 비교합니다. 전후 측정값 차이만으로 코드 수정 효과를 판단하지 않습니다. 저장된 입력을 이용한 재생과 통제된 테스트는 실제 서비스 실행과 별도로 기록합니다.

### 지원 범위와 판정

지원 범위는 도구 목록, 스키마·설명, 실제 응답과 구현으로 조사합니다. 광고되지 않은 조회 도구는 `UNSUPPORTED`로 기록합니다. 기준 MCP는 상대시간 계약을 제공합니다. 절대시간 기능은 계약의 일부이거나 기능 검증이 요청될 때 별도로 점검합니다. 지원하는 상대시간 요청을 형식 오류로 거절하거나 성공 결과의 Period가 호출과 맞지 않으면 `FAIL`입니다. 독립 응답의 수집·완전성 제약이나 기준을 확보할 수 없는 경우는 `UNVERIFIABLE`입니다. AI 실행 실패는 `AI_FAILED`로 구분합니다.

Codex는 이 증거로 책임 영역과 수정 필요성을 판단합니다. 수정할 객관적 근거가 없다면 판정과 이유를 보고하고 작업을 마칩니다.

## 실행 한도와 통제

| 정책 | 강제하는 곳 |
| --- | --- |
| 비교 배치 최대 8분, MCP 호출 45초, HTTP 요청 30초 | `verify.js`, stdio Client와 HTTP Client |
| 고정 구간 검토의 일치 확인, MCP 변경 검토의 깨끗한 실제 기준·성공 후보 근거, Harness 검토의 동일 입력 첨부 | `review.js` 검증과 보고서 빌더 |
| 증거 디렉터리·파일 권한, 알려진 토큰 마스킹, 승인된 프로젝트·필드만 표본에 사용 | 검증·보고 CLI와 공개 정책 |
| 최대 두 번의 수정 시도, 각 분석·수정 8분 및 각 빌드·테스트 2분 목표 | 공식 Codex 작업 지침. 별도 감시 프로세스가 모든 CLI 세션을 제한하지는 않음 |
| 후보 분리, 보존 정책, 대상 Fork 검증, 최종 GitHub Merge 및 제공자 공개 승인 확인 | 작업 지침, 설정과 사람의 검토. GitHub 인증·권한 또는 제공자 승인을 코드가 대신하지 않음 |

공식 비교 배치는 자동 재시도하지 않습니다. Codex가 원인을 분석하고 한도 안에서 다시 실행합니다. 무인 실행에서 전체 제한이 필요한 경우 **Harness 루트**의 Bash에서 `timeout --kill-after=10s 35m codex exec "MCP 전체 기능을 검수해 줘"`처럼 운영자가 제한을 설정할 수 있습니다.

Harness 결함이 확인되면 Codex가 그 코드도 수정할 수 있습니다. 이전 버전과 수정 버전에 같은 입력을 제공해 판정 차이를 검사하고, 기존 기준을 유지한 상태에서 원본과 후보를 재검증합니다. 검증 기준 자체의 변경은 구현 수정과 구분하고 사용자 승인을 받습니다. MCP와 Harness가 둘 다 바뀌면 각각 PR을 제출합니다.

## 보안과 기록

인증정보는 환경변수로 전달하며 독립 HTTP 토큰을 MCP 프로세스에 넘기지 않습니다. API Origin은 HTTPS 형식 검사 외에도 사용자가 승인한 데모 주소여야 합니다. API 원문, 프로젝트 코드 및 정확한 시각은 로컬에 보존합니다. PR은 가명 처리된 승인 표본과 판정 근거만 포함합니다. 보호된 경로, 샌드박스, 읽기 전용 토큰, GitHub 검토 절차는 현재 환경의 권한 정책을 따릅니다. [공개 범위와 제출](reporting.md#데이터-공개-설정)

## 설계의 한계와 확장 방향

- 시나리오가 좁으면 어떤 결과가 검증됐는지 해석하기 쉽지만, 등록되지 않은 도구와 자유 형식 AI 답변의 정확성까지 보장할 수 없습니다.
- 표본 필드와 집계 형식을 명시해 독립 비교를 재현할 수 있습니다. 새로운 API 스키마나 데모 데이터 부족에는 별도의 시나리오 또는 검증 환경이 필요합니다.
- Codex에 다음 단계를 맡겨 환경·구현 문제에 유연하게 대응하지만, 작업 시간의 일률적 강제와 PR 대상 선택은 별도 운영 통제에 의존합니다.
- 향후 후보로 시나리오 확대, 새 API 스키마의 모의 응답 회귀 테스트, 조직 CI에서의 변경 범위 검사 강제를 검토할 수 있습니다. 현재 공식 승인 흐름은 GitHub PR입니다.
