# 사용 가이드

[설치 가이드](installation.md)로 계정, Fork, 데모 권한과 로컬 설정을 준비한 뒤 **Harness 루트**에서 `codex`를 엽니다. 명령을 내리기 전에 작업 트리의 기존 변경은 보존해 달라고 요청할 수 있습니다.

## 자연어 요청 예제

[실행 예시](execution.md)에서 요청 후 생성되는 검토 자료를 확인할 수 있습니다.

| 목적 | 요청 예제 |
| --- | --- |
| 전체 검수 | “MCP 전체 기능을 검수해 줘.” |
| 특정 기능 | “APM 트랜잭션 통계와 예외 통계만 검수해 줘.” |
| 데이터 정확성 | “TPS의 Period, 5초 간격, 누락과 값을 독립 HTTP로 대조하고 변경 없이 결과만 알려 줘.” |
| 기능 개선 | “고정 UTC 구간에서 MCP가 조회를 지원하는지 확인하고, 필요하면 상대시간 호환성을 유지해 개선해 줘.” |
| 추가 수정 | “이 PR의 검토 의견을 반영하고 같은 절대 구간에서 재검증해 줘.” |

전체 검수는 현재 등록된 범위를 수행합니다. Codex는 기본 시나리오 6개를 실행하고, 기준 MCP의 상대시간 조회로 [서버 CPU AI 답변 검증](#서버-cpu-ai-답변-검증)을 별도로 실행합니다. 이 단계에서는 MCP 데이터를 캡처하고 현재 Codex가 답변을 작성한 뒤 독립 HTTP로 검증합니다. 두 결과는 보고서에 각각 기록합니다. 모든 MCP 도구의 기능이나 임의의 자연어 답변의 정확성은 범위 밖입니다. 선행 조건을 충족하지 못한 경로는 [기존 실패·검증 불가 판정](#실패-확인-및-재시도)을 적용하고 가능한 검증을 진행합니다.

## 작업 결과에 따른 흐름

| 확인한 상황 | Codex가 하는 작업 |
| --- | --- |
| 검사 범위 내 수정 필요 없음 | 판정, 증거와 한계를 보고 |
| MCP 동작 문제 | 기준과 후보를 분리해 빌드하고 같은 기준으로 재검증한 뒤, 변경이 있는 MCP Fork에 검토용 PR 제출 |
| Harness 문제 | 동일 입력으로 변경 전후 판정 및 정책 유지 여부를 비교하고 별도의 Harness PR 제출 |
| 두 저장소에 변경 필요 | PR을 분리하고 상호 참조. MCP PR에 사용한 Harness SHA 기록 |
| 외부 API 제약·환경 실패 | 실패 원인과 범위를 기록하고 교정 가능한 조건에 한해 재시도. 데이터 부족이나 인증 오류를 MCP 결함으로 단정하지 않음 |

사용자는 GitHub에서 파일 차이, 변경별 반영 근거, 시나리오별 전후 판정 및 승인된 실제 표를 검토합니다. 추가 보완을 요청할 때는 PR URL과 문제가 된 시나리오를 지정합니다. 만족하면 GitHub에서 직접 Merge합니다. [보고서와 PR 제출](reporting.md)

## 직접 검증

`--mcp`에는 Git 체크아웃을 전달합니다. 먼저 그 디렉터리에서 `npm ci`, `npm run build`, `npm test`를 수행해 `dist/index.js`를 준비합니다. 아래 예시는 설치에서 만든 기준 체크아웃을 사용하며, 후보는 별도로 만든 깨끗한 체크아웃을 지정합니다. 검증할 때는 **Harness 루트**와 두 읽기 전용 환경변수가 있는 셸에서 실행합니다.

```bash
node verify.js --list

# 기본 MCP 시나리오 전체
node verify.js --mcp runs/baseline --phase before

# APM 통계·오류 입력과 시계열만 검수
node verify.js --mcp runs/baseline --select apm --select timeseries --phase before
```

`--select`에는 `all`, `server`, `apm`, `timeseries`, `range` 또는 목록에 나온 시나리오 ID를 사용할 수 있고 반복 지정이 가능합니다. `range`는 잘못된 기간 입력 시나리오를 제외한 조회를 선택합니다. `--request`로 로컬 보고서에 요청 요약을 남길 수 있습니다. `--config FILE`의 기본값은 Harness 루트의 `config.local.json`입니다.

### 절대시간 기능 검증

도구 스키마·설명과 구현을 확인하여 고정 UTC 요청이 지원되거나 해당 기능 자체가 요청 범위인 경우 `--feature absolute`를 선택합니다. 고정 기간 MXQL 비교와 혼합·잘못된 날짜·역순 입력 거부를 실행합니다. 기준 도구가 상대시간만 제공한다면 미지원 근거를 보고서에 기록합니다.

전후 비교는 한 번 선택한 종료 시각을 두 명령에 전달합니다. 아래에서 `runs/candidate`는 빌드를 완료한 후보 체크아웃 예시입니다. 기준에서 실패 재현을 예상하는 경우 두 명령을 `&&`로 연결하지 않습니다.

```bash
fixed_end=$(node -p 'Math.floor((Date.now() - 20 * 60_000) / 300_000) * 300_000')
node verify.js --mcp runs/baseline --phase before --feature absolute --fixed-end "$fixed_end"
node verify.js --mcp runs/candidate --phase after --feature absolute --fixed-end "$fixed_end"
```

종료 값은 과거의 5분 경계 UTC Unix 밀리초입니다. 해당 시각까지의 15분을 검증합니다. 명령 옵션을 생략하면 설정의 `fixedEnd`, 둘 다 없으면 실행 시각보다 최소 20분 앞선 최신 5분 경계를 사용합니다. APM 통계는 v2 집계 대조를 위해 5분 경계를 사용합니다. 서버만 선택하면 `--select server-absolute --fixed-start START_MS --fixed-end END_MS`로 밀리초 경계를 지정할 수 있습니다. 동일 기간의 반복 결과를 확인할 때는 두 경계와 나머지 조건을 그대로 재사용합니다. PromQL 시간 전달처럼 독립 참조가 별도로 필요한 기능은 대상 MCP의 통제된 HTTP Fixture에서 전송한 요청을 확인하고 테스트를 검토 자료에 첨부합니다.

### 상대시간 전후 검증

같은 선택, 프로젝트 설정과 기준으로 기본 배치를 실행합니다. 각 MCP 응답의 Period에 대한 HTTP 참조로 별도 판정합니다. 경계나 데이터 의존 결함은 저장 응답 재생, 같은 입력 또는 테스트 Fixture로 재현합니다.

## 후보 확정과 제출 순서

객관적 근거를 분석해 수정할 문제가 있으면 아래 단계로 진행합니다. 변경이 없다면 판정과 근거 및 한계를 보고합니다.

1. 별도 MCP 작업 브랜치에서 코드를 수정합니다.
2. 후보를 빌드해 Git이 추적하는 배포 산출물을 갱신합니다. 예를 들어 `dist/index.js`와 소스맵이 변경될 수 있습니다.
3. 단위 및 회귀 테스트를 실행합니다.
4. 변경한 소스·테스트와 해당 배포 산출물을 커밋합니다. 후보에서 `git status --porcelain`의 출력이 비어 있는지 확인하고 `git rev-parse HEAD`로 전체 후보 SHA를 기록합니다.
5. 같은 후보에서 최종 독립 실데이터 검증을 실행합니다. 기준과 후보의 절대 구간에는 같은 `--fixed-end`를 사용합니다.
6. 전체 검수라면 동일 후보에서 [서버 CPU AI 답변 검증](#서버-cpu-ai-답변-검증)을 실행합니다. 캡처로 질문·MCP 데이터를 확보하고 Codex가 답변을 저장한 뒤 독립 HTTP를 조회합니다.
7. MCP와 AI 답변 판정, 테스트, 증거의 후보 SHA를 확인하고 [보고서를 생성해 검토](reporting.md#codex의-보고서-생성)합니다.
8. 검증한 커밋이 Push 및 PR의 head와 일치하도록 확인합니다. 후보나 산출물이 변경되면 새 커밋에서 최종 검증과 보고서 생성을 다시 진행합니다.

## 실패 확인 및 재시도

| 종료 코드 | 의미 | 확인 시점 |
| --- | --- | --- |
| `0` | 등록 범위 검증 통과 | 실행의 시나리오 결과와 판정 근거 확인 |
| `1` | 검증 실패 | 저장된 MCP 응답과 독립 HTTP 응답의 조건·키 대조 |
| `2` | 기능 미지원, 검증 불가 또는 환경·인증 문제 | 토큰 전달 및 프로젝트 권한, 네트워크, 시간 범위와 기준 데이터 확인 |

출력에 표시된 `runs/<실행 ID>/report.md`와 `report.json`에서 사유 코드를 확인합니다. 환경 오류는 먼저 인증, 권한 또는 네트워크 상태를 복구합니다. 독립 API가 빈 결과를 제공하거나 완전성을 확인할 수 없는 구간에서는 해당 한계를 보고합니다. Codex가 재시도 여부를 판단할 때 [시간과 승인 정책](architecture.md#실행-한도와-통제)을 따릅니다. 자료를 외부에 공유할 때는 [공개 설정](reporting.md#데이터-공개-설정)을 적용합니다.

## 서버 CPU AI 답변 검증

지정한 서버 한 대의 최근 1분, `cpu`(%), 표본 수·평균·최대에 대해 **Codex가 작성한 JSON 답변 자체**를 비교합니다. 전체 검수에서는 기본 6개 MCP 검증에 이어 이 절차를 수행합니다. 이 절차만 별도로 실행할 수도 있습니다. 서버 식별자는 해당 프로젝트의 권한 있는 MCP 서버 조회에서 골라 로컬로 전달합니다.

1. Harness 루트에서 서버를 정하고 최근 1분을 캡처합니다. 고정 UTC 조회를 지원하는 빌드에서 같은 과거 1분을 재현할 때는 정렬된 종료점을 `--end-ms`로 선택할 수 있습니다. 예시는 빌드가 완료된 `runs/candidate`를 사용합니다.

   ```bash
   read -r -p '검증할 서버 식별자: ' server_id
   node verify-ai.js capture --mcp runs/candidate --server="$server_id"
   ```

2. 현재 Codex 세션에 캡처 출력의 질문과 MCP 행으로 답하도록 요청합니다. Codex는 독립 HTTP 결과나 기존 정답을 읽기 전에 최종 답변 JSON을 보호된 로컬 파일에 저장합니다. 파일 전체가 검증하는 답변입니다. 캡처는 MCP 토큰만 하위 프로세스에 전달합니다. MCP 호출은 프로젝트 범위의 서버 테이블을 읽고, 캡처 단계에서 지정 서버의 행만 Codex에 전달합니다.
3. 답변을 제출합니다. `capture_dir`에는 캡처 출력의 디렉터리, `answer_file`에는 저장한 답변 JSON 경로를 지정합니다. 검증기는 제출 내용을 먼저 저장하고, 호출 시각과 대조한 MCP Period로 같은 프로젝트와 지표를 독립 HTTP에서 조회합니다. AI가 실행되지 않았다면 `--answer` 대신 `--ai-failed`를 사용합니다.

   ```bash
   read -r -p '캡처 디렉터리: ' capture_dir
   read -r -p '답변 JSON 경로: ' answer_file
   node verify-ai.js verify --capture "$capture_dir" --answer "$answer_file"
   ```

독립 기준은 선택 서버의 시작 포함·종료 제외 5초 격자 12개, 유일한 시각과 0~100 범위의 유효한 CPU 값입니다. 각 행에 동일 가중치를 사용합니다. 실제 HTTP 원값으로 평균과 최대를 계산하고, HTTP 행에 MCP의 소수 둘째 자리 표시 규칙을 적용한 뒤 평균과 최대를 다시 계산합니다. 답변은 표시 기준 결과를 소수 둘째 자리로 반올림한 값과 정확히 일치해야 하며, 원값 결과와의 차이는 부동소수점 여유를 포함해 0.01%p 이내여야 합니다. 표본 수와 프로젝트·서버·기간·지표·단위는 정확히 일치해야 합니다.

MCP 판정과 AI 판정은 분리됩니다. 누락·중복 등으로 독립 기준이 불완전하면 해당 수치 판단은 `UNVERIFIABLE`입니다. 잘못된 수치나 응답 형식은 `FAIL`, AI 실행 실패는 `AI_FAILED`입니다. 두 판정이 모두 PASS면 종료 코드 0, 실패는 1, 검증 불가는 2입니다. 자유 형식 문장의 정확성은 이 시나리오의 범위 밖입니다. JSON이 사용자에게 제공하는 검증 대상 답변입니다.

## AI 실패 진단

Harness 루트에서 `node run.js --failure-example`로 의도적으로 실패하는 하위 프로세스의 분류와 보고를 재현할 수 있습니다. `node run.js --agent-smoke`는 기존 Codex 초기화 진단이며 CLI 인증과 네트워크가 필요합니다. 두 명령의 증거와 적용 범위는 [실패 처리 근거](execution.md#실패-처리-근거)를 참고하세요. 공식 검수 흐름은 현재 Codex 세션에서 `verify.js`와 `verify-ai.js`를 호출합니다.
